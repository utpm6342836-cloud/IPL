# ナレッジ設計

## 1. 載せるもの・載せないもの

| 区分 | 文書 | 載せる | 理由 |
| --- | --- | --- | --- |
| 標準フロー | 00_はじめに、01_全体像 | ○ | STEPの判断、戻るタイミング、相談先 |
| 標準フロー | STEP0〜8 の手順書（9ファイル） | ○ | 手順番号で「次にやること」を示すため |
| 標準フロー | ひな形集（templates を1ファイルにまとめたもの） | ○ | ひな形をその場で示すため |
| 標準フロー | 90_発明塾手法との対応 | △ | 利用条件の確認（U1）後に判断 |
| 標準フロー | 99_出典と改訂履歴 | ○ | 出典の案内、版の確認 |
| 標準フロー | 91〜93（呼び方・検証・体制） | × | 標準化チーム向けで、利用者への回答には使わない |
| 共有 | SharePoint構成案・動画シリーズ構成案 | × | 利用者向けではない |
| 原資料 | 発明塾の PDF・pptx | × | 転載禁止の表示があるため |
| 案件 | 個別の案件ファイル・ヒアリング記録 | × | アクセス権の異なる情報が混ざるのを防ぐため。案件の情報は会話の中で利用者が貼る |

## 1-2. 子エージェント「Web調査」の検索先

案内役のナレッジとは別に、子エージェントに公開サイトを登録する。候補と考え方は [エージェント構成.md](エージェント構成.md) の3章。

## 2. ファイルの形

- 1STEP1ファイル。ファイル名は `IPL_STEP1_顧客価値仮説` のように、番号と名前を入れる。
- 見出しの階層をそろえる（`## やり方` → `### 1-1 …`）。
- 各ファイルの先頭に「IPL標準フロー v1.1／STEP1」と版とSTEPを書く（手順書には記載済み）。エージェントが回答に版を示せるようにするため。
- Markdown から Word（.docx）に変換して SharePoint に置く場合の例（Pandoc を使う場合）：

```bash
pandoc docs/steps/STEP1_顧客価値仮説.md -o IPL_STEP1_顧客価値仮説.docx
```

（変換後、表とコードブロック（ロジックツリーの図）の崩れを目で確かめる。）

## 3. 更新の流れ

1. 正本（このリポジトリ）を直す。
2. 改訂履歴に版・日付・変更点を書く。
3. Word に変換し、SharePoint の「エージェント用ナレッジ」フォルダの同じファイル名で上書きする（バージョン履歴が残る）。
4. Copilot Studio 側の再読み込みの状況を確かめ、テスト質問のうち変更に関係するものを再実行する。

## 4. 確かめていないこと

- SharePoint のフォルダをナレッジにした場合、更新が回答に反映されるまでの時間は、本版では確かめていない。パイロットで実測する。
- 見出しをそろえることで回答の精度が上がるかは、Copilot Studio の内部の検索方法に依存する。テスト質問で比べる（見出しあり／なしの2版で比べると確かめやすい）。
