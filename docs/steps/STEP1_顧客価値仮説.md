# STEP1　顧客価値仮説（売れる）

> IPL標準フロー v1.2／STEP1　（全体像：[01_全体像.md](../01_全体像.md)）

## このSTEPでやること

**「最初に誰が買うか（一社・一人）」と「なぜ買うか（どんな困りごとが解決するか）」**の仮説を、手元の情報で書きます。

必ずやるのは 1-1〜1-3 の3つだけです。下の「深めるときの観点」は、必要なときに使います（エージェントが状況に応じて声をかけます）。仮説の確からしさは、このあとの検証ループ（STEP4〜7）で何度も確かめるので、ここで完璧にしなくてかまいません。

## なぜ必要か

最初の一人が買わないものは、大きく売れる見込みが薄いからです。「自動車業界」「医療機関」のような大きな括りのままだと、競合も使う場面も見えず、調べることも決まりません。

## 始める前にそろえるもの

- お題シート、エッジ情報カード（STEP0）
- 手元の情報：依頼者のメモ、社内の技術資料、最近気になった記事や特許など

目安：合計1〜2日。手元の情報（社内を含む）で立て、本格的な調査は STEP4・5 に回します。

## やり方（必須）

### 1-1　顧客候補を挙げ、ファーストユーザーを1つ決める（60〜90分）

- STEP0 のお題とエッジ情報カードの「将来の予想（誰に機会が生まれるか）」から、顧客候補を3〜5つ挙げます。
- 「直接のお客様」と「その先のお客様」を分けて書きます（例：材料なら、直接＝部品メーカー、その先＝完成品メーカーや消費者）。
- 候補ごとに、次の5つを1〜5点で仮に付け、会いに行く順番を決めます：困りごとの強さ／困る頻度／今の手段への不満／予算・決裁権／会いに行ける可能性。点数は買ってくれる証拠ではありません。
- 一番上の候補をファーストユーザーにし、「この会社（人）に会って話してみたい」理由を1〜3行で書きます。
- [templates/03_困りごとシート_ロジックツリー.md](../../templates/03_困りごとシート_ロジックツリー.md)
- エージェントに頼めること：顧客候補の洗い出し、候補の会社の特許・決算資料の要約。自分でやること：どの候補が近いかの判断、元の資料の確認。

### 1-2　困りごとを書き、「死活問題か」を一度だけ問う（45〜60分）

- 今のやり方（As-Is）、本当に達成したいこと（To-Be）、その間を妨げているもの、今は何で代用しているか（その費用・損失・不満）を書きます。
- 「薄い」「熱に強い」のような機能と、「作業が止まらない」「目立たない」のような得たい成果を分けます。
- 最後に1つだけ問います：**「これが解決しないと、顧客の事業・生活が立ち行かなくなるか（死活問題か）」**。答えは「はい／いいえ／分からない」でかまいません。「いいえ」でも先に進めます。STEP7 で顧客に確かめます。
- あわせて自分に問います：**「その課題、ホントなの？」** 書いた困りごとは、顧客の言葉や行動から来たものですか、それとも自分たちの技術に都合のよい解釈ですか。根拠が自分たちの推測だけなら「予想」と書き、STEP7 で顧客に確かめる行にします。
- このSTEPでは「自社で作れるか」は考えません（STEP2 で書きます）。作れることから考えると、「作れるけど売れない」ものになりやすいためです。

### 1-3　価値の仮説を1文にする（30分）

> ［顧客］は［場面］で［今の手段］のために［具体的な損失］を受けている。［指標］を［目標値］まで改善できれば、［お金を払う人］が［対価］を払う可能性がある。

- 指標は顧客の判断に直結するものを3つまでにします。
- 顧客本人に聞いて「そうだ／違う」と答えられる文になっているか確かめます。
- [templates/04_価値仮説_企画骨子.md](../../templates/04_価値仮説_企画骨子.md)
- あわせて [templates/05_仮説検証シート.md](../../templates/05_仮説検証シート.md) の「売れる」の2行（H1 本当の課題か、H2 ファーストユーザーは誰か）に仮説を書きます。このシートは STEP8 まで同じ1枚を書き足していきます（[02_4つの基準.md](../02_4つの基準.md)）。

## 深めるときの観点（任意）

必須ではありません。「こういうとき」に当てはまったら使います。エージェントは、当てはまりそうなときに1つずつ提案します。

### 観点A　社内の情報を俯瞰する

- **使うとき**：社内で似た検討をした覚えがある／自社の技術・特許・過去の顧客の声がありそう／新しい分野で何から手を付けるか迷う。
- **やり方**：技術・研究、自社特許、過去の検討（見送った理由）、顧客の声、契約、会社の方針が「どこに・何があるか・詳しい人は誰か」を1枚にする。
- **AIの使い方**：Microsoft 365 Copilot（社内の文書・メール・会議を横断して要約できる機能）に、お題に関係する社内の資料を探して要約させ、上の枠組みに当てはめて整理させる。Copilot が見られるのは、その人がアクセスできる資料だけなので、見つからないことは「社内にない」ことを意味しない。要約は確かさのランクB以下として扱う。
- [templates/02a_社内情報と外部環境の俯瞰.md](../../templates/02a_社内情報と外部環境の俯瞰.md)

### 観点B　外部の制約と追い風を下調べする

- **使うとき**：規制・認証が関わりそうな分野／社会や政策の動きが強く効きそうなお題／自社や業界のトップが方向性を示している。
- **やり方**：お題に関係する制約・追い風を**最大3つ**だけ書く（規制、社会の動き、自社・業界トップの発言など）。PESTEL の全部の欄を埋める必要はない。
- **AIの使い方**：調査エージェント（Web調査）に、お題と顧客の仮説を渡して「関係しそうな規制・政策・トップの発言を出典付きで3つまで」と頼む。ここでは仮置き（ランクB以下）。本当に効く制約かは、STEP4 の調査計画に入れて STEP5 で確かめる。
- 発言は「誰が・いつ・どこで・何と言ったか（出典）」と「そこからの読み」を分ける。

### 観点C　課題を3つの見方で深める

- **使うとき**：困りごとが「あったら便利」程度に見える／なぜ今まで解決されていないのかが説明できない／競合がすでに解決していそう。
- **やり方**：

| 見方 | 問い | 強い課題のしるし |
| --- | --- | --- |
| ① 死活問題か | 解決しないと、顧客の事業・生活が立ち行かなくなるか | 予算がすでにある。期限がある。それなしには過ごせない |
| ② まだ見つかっていない課題か | 顧客自身もまだ言葉にしていないが、これから表に出る課題はないか（規制の強化、技術の世代交代、トップの方針から先読みする） | 変化の時期が読める。先に気づいた人が少ない |
| ③ 何が足りなくて解決できていないか（ラストワンピース） | 解決に向けた取り組みはあるのに、何か1つが足りないために止まっていないか。誰がどこまで取り組み、どこで止まっているか | 足りない1つがはっきりしている。それを自社が持てそう |

- 道具：課題‐解決ロジックツリー（顧客の成果 ─ 妨げる現象 ─ 原因 ─ 解決の原理、右端に「止まっている理由」）と、トレードオフ（Aを良くするとBが悪くなる）。
- 3つの見方は、仮説の段階ではすべて予想です。確からしさは検証ループ（特に STEP7 のヒアリング）で高めていきます。

## 発明塾のコツ

- 顧客は「セグメント」ではなく「まず一社・一人」。「会いたい」「提案してみたい」と思えるところまで深めると、ファーストユーザーが自然に「決まる」（発明塾式 企画術3日目）。
- 網羅的な分析から始めず、手元の情報から大胆な仮説を立て、次の情報へ進む（同2日目）。必須を3つに絞っているのはこのため。
- 「その課題、ホントなの？」を徹底して問う。顧客の課題を自分たちの都合のよい方向に解釈することは日常的に起きる。「できるかどうか分からないが、ものすごく必要とされているもの」を突き止めることが先で、作り方はその後で考える（発明塾メールマガジンの解説の要約）。
- それなしには過ごせないクリティカルな課題を狙い、課題を先読みし、誰がどこで止まっているかを読む（企業内発明塾 紹介資料、情報探索術1日目）。観点Cはこの考え方による（「ラストワンピース」は本フローでの呼び方。参照した資料の中ではこの言葉そのものは確認していない）。

## できあがるもの

- 必須：困りごとシート（ファーストユーザー、困りごと、死活問題かの答え）、価値の仮説（1文）
- 任意：社内情報と外部環境の俯瞰表、課題の3つの見方、課題‐解決ロジックツリー

## 次に進む前のチェック（自分で）

- [ ] ファーストユーザーが会社名・部署（または具体的な人物像）まで書けている
- [ ] 直接のお客様とその先のお客様を分けて考えた
- [ ] 価値の仮説が、顧客に聞いて賛否を判断できる文になっている

## 困ったら

- ファーストユーザーがどうしても1社に決まらない → 2社まで残して STEP2 に進み、STEP7 のヒアリングで決める。
- 困りごとが弱い気がする → 観点Cを使う。それでも弱ければ、顧客を変えるかお題を見直す。
- 社内に似た検討がありそう → 観点Aを使う。IPL担当・研究企画・営業企画に「この分野を知っている人」を聞く。

## よくある失敗

- 「これなら作れる」から考え始め、顧客の課題を後から当てはめる（作れるけど売れない、になる）。
- 顧客の課題を、自分たちの技術に都合のよい方向に解釈する。

- 観点（PESTEL、3つの見方など）を全部やろうとして、STEP1 から先に進まない。
- 特許の「課題」欄に書かれていることを、そのまま顧客の困りごとの証拠にする（出願した会社の見方であって、顧客の声ではありません）。
- 直接のお客様は困っていても、その先のお客様は困っていないことを見落とす。
