# AIの品質を保つ仕組み

> IPL標準フロー v1.2　対象：標準化チーム・IPL担当・エージェント作成担当

## 1. 考え方：1つの仕組みでは保てないので、5つの層を重ねる

生成AIの回答は、同じ質問でも毎回少しずつ変わり、もっともらしい誤り（存在しない特許番号、出典と違う要約など）を含むことがある。1つの仕組みで誤りをなくすことはできないため、**作る段階・公開前・回答ごと・運用中・人の確認**の5つの層で、誤りが利用者の判断まで届かないようにする。

| 層 | 何をするか | 誰が | いつ | 防げること | 防げないこと |
| --- | --- | --- | --- | --- | --- |
| 1 作りで防ぐ | 指示文・ナレッジ・検索先を絞る（番号を作らない、ランクは最高B、社外秘を検索しない） | エージェント作成担当 | 作るとき | よくある誤りの多く | 指示を守らない回答 |
| 2 公開前に試す | テスト質問（30問）を一括で実行し、合格基準を満たすまで直す | 標準化チーム | 公開前・改訂のたび | 改訂で悪くなること（後戻り） | テストにない質問での誤り |
| 3 回答ごとに点検する | 検証エージェント（チェック役）が、回答を決まった観点で点検する | 利用者が呼ぶ（重要な回答のとき） | 判断メモ・情報リストなど重要な出力のとき | 出典の抜け、事実と予想の混在、禁止事項 | 出典の中身の正しさ（元資料を開かないと分からない） |
| 4 運用中に見張る | 会話記録を月1回抜き取って点検、利用者の評価（よい／よくない）を集計、AIの間違いの記録を集める | 標準化チーム・IPL担当 | 毎月 | 実際の使われ方での誤りの傾向 | 記録されない誤り |
| 5 人が確かめる | 確認ポイント①②、確かさのランク（人が元資料を開いたらA）、判断は人がする | 利用者・IPL担当・意思決定者 | STEP3後・STEP7後・STEP8 | 誤りが判断に使われること | — |

**いちばん大事なのは層5。** 層1〜4は、層5で人が確かめる量を減らし、見落としを減らすためのもの。AIの回答をそのまま判断の根拠にしない、というルールは、どの層を足しても外さない。

## 2. 層2：公開前のテスト（Copilot Studio の評価機能を使う）

Copilot Studio には、質問の一覧（テストセット）を取り込んで一括で試し、採点方法（グレーダー）で合否を出す評価の機能がある。検索で確認できた範囲では、次のことができる（いずれも Microsoft の発表・文書の要約。画面で最新の状態を確かめること）。

- 質問の一覧を CSV などで取り込める。
- 採点方法として、文字の一致、意味の近さ（類似度）、回答の質などを選べる。
- 1つのテストセットに複数の採点方法を当てられる（2026年2月に一般提供と発表）。
- 版ごとに結果を比べられる。

出典：Microsoft Copilot ブログ「How to evaluate AI agents」https://www.microsoft.com/en-us/copilot/blog/copilot-studio/how-to-evaluate-ai-agents/ 、リリースプラン「Evaluate test sets with multiple graders」（検索結果で確認。原ページは Microsoft Learn のリリースプラン）、「New and improved: Agent evaluations…」https://www.microsoft.com/en-us/copilot/blog/copilot-studio/new-and-improved-agent-evaluations-computer-use-and-advanced-maker-training/

### 運用

| 項目 | 内容 |
| --- | --- |
| テストセット | [copilot-studio/テスト質問.md](../copilot-studio/テスト質問.md) の30問。取り込み用の一覧は [copilot-studio/テストセット.csv](../copilot-studio/テストセット.csv)（列の並びは、取り込み画面の見本に合わせて調整する） |
| 実行のタイミング | 指示文・ナレッジ・子エージェントを変えたとき。毎月の点検のとき |
| 合格の目安（仮） | 「してはいけないこと」に関する質問（T08・T12・T15・T16・T24・T25・T28）は全問合格。その他は8割以上 |
| 不合格のとき | 指示文・説明・ナレッジを直し、もう一度全問を流す（直したところ以外が悪くなっていないかも確かめる） |

### 限界

- 採点方法「回答の質」もAIが採点するため、採点自体が間違うことがある。不合格だけでなく、合格の回答も一部は人が読む。
- テスト質問にない聞き方では、結果が違うことがある。運用中に見つかった誤りの質問を、テストセットに足していく（層4とつなげる）。

## 3. 層3：検証エージェント（チェック役）

### 役目

案内役や調査役の回答を、決まった観点で点検し、問題のある箇所を一覧にして返す。**直すのは利用者**で、チェック役は書き換えない。

### 点検する観点

| No | 観点 | 例 |
| --- | --- | --- |
| C1 | 事実に出典（URL・特許番号など）が付いているか | 「市場は年10%成長」に出典がない |
| C2 | 事実・予想・未確認が分かれているか | 予想を事実のように書いている |
| C3 | 確かさのランクの付け方がルールどおりか | AIが読んだだけの情報をランクAにしている |
| C4 | 特許番号・URLの形がおかしくないか、出典のない番号がないか | 桁数や形式が不自然な番号 |
| C5 | 禁止事項に触れていないか | FTOの結論、Go/No Goの断定、「特許がない＝自由に使える」 |
| C6 | 「調査で判明した」などの言い切り、大げさな表現 | 「確実に」「圧倒的」 |
| C7 | 反証・見落としが添えられているか | 支える情報だけが並んでいる |
| C8 | 手順書と食い違っていないか | 手順書にない社内ルールを書いている |

指示文：[copilot-studio/検証エージェント指示文.txt](../copilot-studio/検証エージェント指示文.txt)

### 呼び方

- 利用者が「この回答を点検して」と頼んだとき。
- 判断メモ（STEP8）と情報リスト（STEP5）の下書きを出すときは、案内役が「点検しますか」と勧める。
- すべての回答を自動で点検すると、時間とメッセージ消費が増えるため、重要な出力に絞る。

### 限界（重要）

- チェック役も同じ種類のAIなので、同じ誤りを見落とすことがある。
- **出典が本当にその内容を書いているかは、元の資料を開かないと確かめられない。** チェック役は「出典が付いているか」「形がおかしくないか」までで、中身の正しさは保証しない。
- そのため、チェック役で問題がなかった回答も、判断に使う情報は人が元資料を開いて確かめ、ランクAにする（層5）。

## 4. 層4：運用中の見張り

| 何を | どうやって | 頻度 | 担当 |
| --- | --- | --- | --- |
| 会話記録の抜き取り点検 | 会話記録から20件を抜き出し、検証の観点（C1〜C8）で人が点検する | 毎月 | 標準化チーム（IPL担当が交代で） |
| 利用者の評価 | 回答への「よい／よくない」の評価と、コメントを集計 | 毎月 | 標準化チーム |
| AIの間違いの記録 | STEP8 のノウハウ集・振り返りアンケート、IPL担当の相談ログから集める | 毎月 | 標準化チーム |
| テストへの追加 | 見つかった誤りの質問をテストセットに足す | 毎月 | 標準化チーム |

会話記録の保存場所・閲覧できる人・保存期間は、情報システム部門と決める（社外秘の内容を含むため）。

### 見る数字（目安）

| 数字 | 意味 |
| --- | --- |
| 抜き取り点検での問題の割合 | 下がっていればよい |
| 「よくない」評価の割合 | 同上 |
| テストセットの合格率 | 改訂のたびに下がっていないか |
| 確認ポイント①②でIPL担当が指摘した件数（AI由来のもの） | AIの下書きの質の目安 |

## 5. 段階との関係

| 段階 | 入れる層 |
| --- | --- |
| 2026年度（〜3月）の配布前 | 層1・2・5（必須）、層3（試行） |
| 配布後 | 層4を毎月 |
| 2027年度 | 層3を本運用にするか、パイロットの結果で決める |

## 6. 反証・見落としのリスク

- 層を重ねても誤りはゼロにならない。利用者が「AIが点検したから正しい」と思い込むと、かえって危ない。説明会・動画で「点検は出典の有無まで、中身は人が確かめる」を伝える。
- 点検の負担が大きいと続かない。月20件の抜き取りが回らない場合は、件数を減らすか、重要な出力（判断メモ）に絞る。
- 評価機能の画面・採点方法は変わることがある。取り込み形式やテスト数の上限は、作業時に Microsoft Learn で確かめる。
