# 体制・品質・蓄積の論点（たたき台）

> IPL標準フロー v1.2　対象：標準化チーム・IPL担当・関係部門

ロードマップの図で「？」になっている3つの論点に対する、手順書側からの案。いずれも社内の事情（人数・既存の仕組み）を確かめていないため、検討の出発点として扱ってほしい。

## 前提（ロードマップの図から）

| 時期 | 進め方 |
| --- | --- |
| 2026年度（〜12月：手順書、〜3月：エージェント作成） | SBU・研究開発の人が、IPL担当に教わりながら仮説の立案と検証を行う |
| 2027年度〜 | SBU・研究開発の人が、手順書を読み込んだAIエージェントとチャットしながら進め、分からない点をIPL担当に聞く。IPL担当は標準化チームにフィードバックする |

## 論点1：品質はどう保つか

> AIの回答の品質については [95_AIの品質を保つ仕組み.md](95_AIの品質を保つ仕組み.md) で5つの層に整理した。

### 案

| 仕組み | 中身 | 手順書の場所 |
| --- | --- | --- |
| 2つの確認ポイント | 調べ始める前（STEP3後）と、決める前（STEP7後）に、IPL担当が見る | STEP3 3-7、STEP7 7-10 |
| 確かさのランク | 判断の主な根拠はランクA・B（人が元資料を確かめたもの）だけ | STEP5 5-4、STEP8 8-4 |
| 自分でできるチェック | 各STEPの「次に進む前のチェック」 | 各STEP |
| エージェントの制限 | FTOの結論を出さない、特許番号を作らない、Go/No Goを決めない | copilot-studio/エージェント指示文.txt |
| エージェントのテスト | 改訂のたびにテスト質問18問を実行 | copilot-studio/テスト質問.md |
| 事後の振り返り | 1〜2年後に判断の当たり外れを確かめる | STEP8 8-8 |

### 反証・見落としのリスク

- 確認ポイントがIPL担当の人数に対して多すぎると、IPL担当が詰まり、利用者が待つことになる。案件数の見込みと、IPL担当1人が1か月に見られる件数を見積もる必要がある（未確認）。
- 2027年度以降、確認ポイントを「省略可」にすると品質が下がる可能性がある。案件の大きさ（小・中・大）で、確認の濃さを変える案が考えられる（例：小は確認①のみ、大は両方＋別の人のレビュー）。
- エージェントの回答品質は、Microsoft 側の仕様変更でも変わる。テスト質問の定期実行が必要。

## 論点2：知見やアウトプットをどうためて、フィードバックするか

> IPL担当に集まる知見の回収は [96_知見を回収して標準フローに戻す仕組み.md](96_知見を回収して標準フローに戻す仕組み.md) で具体化した（相談ログ → 月1回のIPL担当会 → 修正リスト → 四半期改訂）。

### 案

```text
利用者 ─(案件ごと)→ 案件ライブラリ（判断メモ・仮説の記録・ノウハウ集）
   │
   └─(振り返りアンケート)→ 標準化チーム ─(四半期ごとに集計)→ 手順書の改訂 → エージェントのナレッジ更新
IPL担当 ─(確認ポイントでの指摘・よくある質問)→ 標準化チーム
```

| ためるもの | 置き場所（案） | 誰が使うか |
| --- | --- | --- |
| 判断メモ・仮説の記録・ノウハウ集 | SharePoint の案件ライブラリ（案件ごとにアクセス権） | 次に似た案件をする人、IPL担当 |
| 検索式・名寄せ表 | 同上（再利用しやすいよう分野別のフォルダも作る） | IPL担当、利用者 |
| 振り返りアンケート | Microsoft Forms などで集計（ツールは未定） | 標準化チーム |
| IPL担当への質問と回答 | よくある質問ページ | 利用者、エージェントのナレッジ |
| エージェントの間違い | 標準化チームの記録表 | エージェントの指示文の改訂 |

### 反証・見落としのリスク

- 案件の記録をエージェントのナレッジに入れると、アクセス権の違う情報が他の人に見える可能性がある。初版では、案件の記録はエージェントのナレッジに入れない（[copilot-studio/ナレッジ設計.md](../copilot-studio/ナレッジ設計.md)）。
- アンケートは回答率が下がりやすい。15分以内に答えられる量に絞り、回答しないと案件が「完了」にならない運用も考えられる（運用の負担とのバランスは未検討）。
- 「ためる」だけでは使われない。次の案件の STEP0（お題設定）で「似た過去案件を探す」手順を入れることを検討する（v1.2 では入れていない）。

## 論点3：社内の他の取り組み（R&Dプラットフォームなど）との連携

本版では、社内の他の取り組みの中身を確認していない。連携を考えるときの確認事項だけを挙げる。

| 確認事項 | 理由 |
| --- | --- |
| その取り組みは、どのSTEPに当たる情報・成果物を持っているか（例：研究テーマの一覧、技術シーズ、顧客の声） | STEP1・2 の「手元の情報」として使えるかもしれない |
| その取り組みに、テーマの審査・ステージゲートがあるか | STEP8 の意思決定と二重にならないよう、判断メモの形をそろえる |
| 使っているツール・置き場所（SharePoint、Teams、専用システムなど） | 案件ライブラリやエージェントの置き場所をそろえる |
| 担当部署と、IPL担当・標準化チームとの役割分担 | 利用者から見て相談先が分からなくなるのを防ぐ |

### 反証・見落としのリスク

- 別の取り組みにすでにテーマ審査の仕組みがある場合、本フローの STEP3・8 と重なり、利用者が同じことを2回書くことになる可能性がある。その場合は、本フローの調査目的シート・判断メモを、既存の審査書類に合わせて作り直すほうがよい。

## 論点4：依頼部門が自走で行うIPLの把握（備忘録 2026-11-24）

### メモ（ユーザー記載の要旨）
- 依頼部門での自走IPLが増えたときも、知財アナリスト（IPL担当）が行うIPLと同様に把握しておく。
- 把握するもの：レポート（成果物）、意思決定の行方（Go / No Go とその後）、有用性。

### 実現の案（未検討・たたき台）
| 何を | どうやって | 負担を軽くする工夫 |
| --- | --- | --- |
| 案件があること | STEP0（お題設定）の時点で、案件台帳（SharePoint のリストなど）に1行登録する（案件コード・部門・担当・お題・大きさ） | 登録はエージェントの最初の案内に組み込む。5項目程度に絞る |
| 成果物 | STEP8 の判断メモを、案件ライブラリに保存する | 判断メモの1枚目だけでよい |
| 意思決定の行方 | STEP8 の意思決定の記録と、1〜2年後の振り返り（8-8） | 振り返り日に、標準化チームから声をかける |
| 有用性 | STEP8 の振り返りアンケート（依頼者・担当者） | 論点5の上長アンケートと合わせる |

### 気をつける点（反証・見落とし）
- 把握が「管理・監視」と受け取られると、自走IPLが台帳に載らない「隠れIPL」になり、かえって把握できなくなるおそれがある。目的は、支援と横展開（似た案件の紹介）だと伝える。
- 社外秘・出願前の内容を含む案件は、台帳には案件コードと部門だけを載せ、中身は案件ごとにアクセス権を絞る。

## 論点5：部門の上層部へのアンケート（備忘録 2026-11-24）

### メモ（ユーザー記載の要旨）
- 部門の上層部（上長）にも、依頼者と一緒にアンケートを取り、今年度の自部門のIPLが役立ったかを聞く（上長に把握してもらう意味も込める）。
- ゆくゆくは、上長や部門ごとに意識が低いテーマが分かる。上層部から各部門に取り組ませる圧力としても機能する。

### 実現の案（未検討・たたき台）
- 年度末に1回、部門の上長に短いアンケート（5問程度）：自部門のIPL案件を把握しているか、判断に役立ったか（5段階）、役立った・役立たなかった案件と理由、来年度に取り組ませたいテーマ、支援への要望。
- 依頼者・担当者の振り返りアンケート（STEP8）と同じ案件コードでつなぎ、上長と担当者の評価のずれも見る。
- 集計は標準化チームが行い、STEP9（学習・仕組み化）の材料にする。

### 気をつける点（反証・見落とし）
- 部門・上長ごとの比較を「圧力」として使うと、回答が実態より良く書かれる（評価を気にした回答）おそれがある。比較結果をどこまで開示するか（標準化チーム内／経営層／全社）は、事前に決めておく。
- 「意識が低い」と見えるのは、IPLが合わないテーマ（短期の改良など）を扱っている部門かもしれない。件数や評価の低さだけで判断せず、理由の欄を読む。
- 上長の回答は、担当者の評価に影響するおそれがある。担当者の回答は上長に個別には見せない、などの扱いを決めておく。
