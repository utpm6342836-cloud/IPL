# 体制・品質・蓄積の論点（たたき台）

> IPL標準フロー v1.1　対象：標準化チーム・IPL担当・関係部門

ロードマップの図で「？」になっている3つの論点に対する、手順書側からの案。いずれも社内の事情（人数・既存の仕組み）を確かめていないため、検討の出発点として扱ってほしい。

## 前提（ロードマップの図から）

| 時期 | 進め方 |
| --- | --- |
| 2026年度（〜12月：手順書、〜3月：エージェント作成） | SBU・研究開発の人が、IPL担当に教わりながら仮説の立案と検証を行う |
| 2027年度〜 | SBU・研究開発の人が、手順書を読み込んだAIエージェントとチャットしながら進め、分からない点をIPL担当に聞く。IPL担当は標準化チームにフィードバックする |

## 論点1：品質はどう保つか

### 案

| 仕組み | 中身 | 手順書の場所 |
| --- | --- | --- |
| 2つの確認ポイント | 調べ始める前（STEP2後）と、決める前（STEP6後）に、IPL担当が見る | STEP2 2-7、STEP6 6-9 |
| 確かさのランク | 判断の主な根拠はランクA・B（人が元資料を確かめたもの）だけ | STEP4 4-4、STEP7 7-4 |
| 自分でできるチェック | 各STEPの「次に進む前のチェック」 | 各STEP |
| エージェントの制限 | FTOの結論を出さない、特許番号を作らない、Go/No Goを決めない | copilot-studio/エージェント指示文.txt |
| エージェントのテスト | 改訂のたびにテスト質問18問を実行 | copilot-studio/テスト質問.md |
| 事後の振り返り | 1〜2年後に判断の当たり外れを確かめる | STEP8 8-5 |

### 反証・見落としのリスク

- 確認ポイントがIPL担当の人数に対して多すぎると、IPL担当が詰まり、利用者が待つことになる。案件数の見込みと、IPL担当1人が1か月に見られる件数を見積もる必要がある（未確認）。
- 2027年度以降、確認ポイントを「省略可」にすると品質が下がる可能性がある。案件の大きさ（小・中・大）で、確認の濃さを変える案が考えられる（例：小は確認①のみ、大は両方＋別の人のレビュー）。
- エージェントの回答品質は、Microsoft 側の仕様変更でも変わる。テスト質問の定期実行が必要。

## 論点2：知見やアウトプットをどうためて、フィードバックするか

### 案

```text
利用者 ─(案件ごと)→ 案件ライブラリ（判断メモ・仮説の記録・ノウハウ集）
   │
   └─(振り返りアンケート)→ 標準化チーム ─(四半期ごとに集計)→ 手順書の改訂 → エージェントのナレッジ更新
IPL担当 ─(確認ポイントでの指摘・よくある質問)→ 標準化チーム
```

| ためるもの | 置き場所（案） | 誰が使うか |
| --- | --- | --- |
| 判断メモ・仮説の記録・ノウハウ集 | SharePoint の案件ライブラリ（案件ごとにアクセス権） | 次に似た案件をする人、IPL担当 |
| 検索式・名寄せ表 | 同上（再利用しやすいよう分野別のフォルダも作る） | IPL担当、利用者 |
| 振り返りアンケート | Microsoft Forms などで集計（ツールは未定） | 標準化チーム |
| IPL担当への質問と回答 | よくある質問ページ | 利用者、エージェントのナレッジ |
| エージェントの間違い | 標準化チームの記録表 | エージェントの指示文の改訂 |

### 反証・見落としのリスク

- 案件の記録をエージェントのナレッジに入れると、アクセス権の違う情報が他の人に見える可能性がある。初版では、案件の記録はエージェントのナレッジに入れない（[copilot-studio/ナレッジ設計.md](../copilot-studio/ナレッジ設計.md)）。
- アンケートは回答率が下がりやすい。15分以内に答えられる量に絞り、回答しないと案件が「完了」にならない運用も考えられる（運用の負担とのバランスは未検討）。
- 「ためる」だけでは使われない。次の案件の STEP0 で「似た過去案件を探す」手順を入れることを検討する（v1.1 では入れていない）。

## 論点3：社内の他の取り組み（R&Dプラットフォームなど）との連携

本版では、社内の他の取り組みの中身を確認していない。連携を考えるときの確認事項だけを挙げる。

| 確認事項 | 理由 |
| --- | --- |
| その取り組みは、どのSTEPに当たる情報・成果物を持っているか（例：研究テーマの一覧、技術シーズ、顧客の声） | STEP1・2 の「手元の情報」として使えるかもしれない |
| その取り組みに、テーマの審査・ステージゲートがあるか | STEP7 の意思決定と二重にならないよう、判断メモの形をそろえる |
| 使っているツール・置き場所（SharePoint、Teams、専用システムなど） | 案件ライブラリやエージェントの置き場所をそろえる |
| 担当部署と、IPL担当・標準化チームとの役割分担 | 利用者から見て相談先が分からなくなるのを防ぐ |

### 反証・見落としのリスク

- 別の取り組みにすでにテーマ審査の仕組みがある場合、本フローの STEP0・7 と重なり、利用者が同じことを2回書くことになる可能性がある。その場合は、本フローの依頼シート・判断メモを、既存の審査書類に合わせて作り直すほうがよい。
